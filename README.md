# Сходка — MAX и Telegram

Общее приложение для поиска компании на спортивные встречи, 16+. Один frontend и API обслуживают оба мессенджера: пользователь MAX может присоединиться к встрече из Telegram и наоборот.

## Что подключено

- MAX Bridge и Telegram Mini Apps SDK во frontend.
- Серверная проверка HMAC подписи initData, времени запуска (24 часа), повторяющихся параметров и профиля пользователя.
- Раздельные идентификаторы `max:123` и `telegram:123`: совпадающие числа в разных платформах не означают одного человека. Объединение двух аккаунтов одного человека пока не реализовано.
- Создание профиля при первом входе, самостоятельное указание возраста 16–100 лет. Возраст не подтверждается платформой.
- Общие каталог, создание сходок, заявки, подтверждения, отмена, возрастные ограничения и точный адрес после подтверждения.
- Проверка доступа к личным сходкам и заявкам. Заголовок x-user-id не заменяет проверенную авторизацию.
- Уведомления организатору о заявке, участнику о решении и подтверждённым участникам об отмене через соответствующую платформу.
- Telegram-бот: /start, /help, кнопка открытия Mini App, long polling.
- MAX-бот сохранён; кнопка использует open_app для зарегистрированного мини-приложения.

## Локальный запуск

Node.js 20+ и npm:

```powershell
Copy-Item .env.example .env
npm ci
npm run dev
```

Frontend: http://localhost:5173. API: http://localhost:3000.
В обычном браузере без данных запуска приложение предложит открыть бота.
Для локальной демонстрации можно явно установить `DEMO_MODE=true` в .env. При `NODE_ENV=production` демо всегда запрещено. На Windows npm workspaces требуют разрешённых символьных ссылок/режима разработчика.

## Подключение на Render

1. Опубликуйте frontend и API из этой версии. Существующие адреса проекта: https://shodka-mvp-v2-1.onrender.com/ и https://shodka-mvp-v2.onrender.com — их актуальная работа здесь не проверялась.
2. Frontend: задайте VITE_API_URL равным HTTPS-адресу API перед сборкой.
3. API: задайте WEB_ORIGIN равным origin frontend, MINI_APP_URL равным HTTPS-адресу frontend, NODE_ENV=production и DEMO_MODE=false.
4. В секретах API задайте TELEGRAM_BOT_TOKEN и MAX_BOT_TOKEN. Не помещайте токены в GitHub или переписку.
5. Для Telegram @skhodkaa_bot в BotFather укажите адрес frontend как Main Mini App. Для ответа на /start включите TELEGRAM_BOT_POLLING_ENABLED=true на одном экземпляре API. Активный Telegram webhook необходимо сначала отключить: webhook и getUpdates одновременно не работают. Эта версия реализует Telegram polling, отдельный webhook-обработчик ещё не добавлен.
6. Для MAX зарегистрируйте тот же frontend как Mini App бота t221_hakaton_max_bot. При другом имени задайте MAX_BOT_USERNAME. MAX_BOT_POLLING_ENABLED=true запускает получение команд.
7. Боты требуют постоянно работающего экземпляра API. Засыпающий хостинг задерживает ответы; не запускайте два poller одного бота одновременно.
8. Укажите DATA_FILE на постоянном диске. Пока используется JSON, допускается только один экземпляр API.

Проверка: GET /health, /api/max/status и /api/telegram/status.
Чтобы бот мог присылать личные сообщения, пользователь должен начать диалог/разрешить сообщения в соответствующей платформе. Ошибка доставки не отменяет сохранённую заявку.

## Переменные

См. .env.example. Дополнительно Docker Compose передаёт переменные обоих ботов в API. Для контейнеров выполните `docker compose up --build`. Данные сохраняются в томе shodka_data.

## Проверки

```powershell
npm run typecheck
npm test
```

Интеграционный тест запускает API с временным файлом и заглушками сетевых API мессенджеров. Проверяет вход из двух платформ, общую сходку, заявки в обе стороны, подтверждение, защиту адреса/личных данных, возраст, недействительные и устаревшие подписи, повторяющиеся параметры и запрет демо в production. Не использует реальные токены и не отправляет сообщения.

При проверке в изолированной Windows-среде зависимости были установлены в отдельной копии без workspaces; TypeScript и Vite запускались напрямую. Исходный lockfile зависимостей сохранён.

## API авторизации

Клиент передаёт `x-platform: telegram|max` и исходную строку `x-init-data` из SDK. Сервер проверяет её токеном соответствующего бота. Произвольный x-user-id учитывается только в явно включённом локальном демо.

- GET /api/me: получить/создать свой профиль и признак demo.
- PATCH /api/me с JSON `{ "age": 20 }`: указать возраст.
- Личные маршруты /api/users/:userId/activities и /api/organizers/:userId/applications доступны только владельцу.
- Каталог и публичная карточка доступны без авторизации, точный адрес скрывается.

Старые openapi.yaml и DATA-API.yaml описывают прежний MVP; новые правила входа приведены здесь, эти спецификации требуют последующей синхронизации.

## Что ещё нужно перед полноценным запуском

PostgreSQL и миграции вместо JSON, модерация и жалобы, реальные отзывы, фоновые напоминания и наблюдение за доставкой сообщений. Сейчас напоминания о времени встречи отображаются внутри интерфейса, отдельного планировщика рассылки нет. Живые Mini Apps, разрешения на сообщения и реальные токены проверяются после настройки платформ/хостинга.
